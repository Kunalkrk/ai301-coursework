# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Diagnosis and grounding | The plan's stated cause, read against every step and control in the repro evidence (not just what a thread comment claims) | Fail if the stated cause is contradicted by, or silently ignores, a specific step/control in the repro evidence — a step that isolates the behavior to a different component, a control that still shows the behavior with the blamed mechanism absent, or a step that pins down where in a pipeline the behavior actually first appears. A diagnosis that only cites a thread comment's claim, without checking it against the repro evidence's own steps, does not clear this on citation alone. Otherwise pass. | required |
| Scope | The plan's in-scope/not-in-scope statement (or, if absent, the files/areas and approach actually listed), read against the one behavior the issue describes | Fail if the plan expands beyond the one reported behavior — a rewrite, a migration, a new abstraction layer, an unrelated version bump, a new CI job, or other "while we're in here" work the issue did not ask for — even when framed as fixing the "real" underlying problem the issue is supposedly a symptom of. Explicitly deferring related work with a stated reason is not scope creep; doing that related work anyway, or folding it into "proposed changes," is. Otherwise pass. | required |
| Executability | The plan's named files/areas and its approach or ordered steps | Fail if a stranger could not start without first deciding something the plan left open: no file or area named, an approach described as "look into X," "upstream or vendored, whichever is easier," or "maybe also check," or a choice between stated options or layers left unmade. A named area (even spanning a couple of related modules) whose exact function is still being pinned down does not fail this on its own when the plan names a concrete, already-in-hand method for finding it (a debug trace already run and described, not "I'll investigate") — that is normal for a plan written before the PR, not an open choice. Otherwise pass. | required |
| Test plan decisiveness | The plan's test plan, read against the repro evidence's own steps and artifacts | Fail if the test plan names no specific, observable outcome tied to the fix itself — "run the full test suite," "should feel fast," "shouldn't panic anymore" with nothing named to check. A decisive test plan re-runs or adapts the repro evidence's own steps (or a control from it) and states what should be observed after the fix that wasn't observed before. Otherwise pass. | required |
| Honesty | Claims about completeness, certainty on untested platforms/conditions, or confidence in the fix working, that the Diagnosis, Scope, and Test-plan checks did not already grade | Fail if the plan claims the fix is complete or proven, claims something works on a platform/condition it hasn't tested, or states a cost/trade-off as negligible without having measured it — without flagging the gap. Do not re-grade here whether the stated cause itself is grounded (that is Diagnosis's job) or whether a deferral is the right scope call (that is Scope's job); a cause the Diagnosis check already passed as grounded in the repro evidence is not re-litigated as dishonest here. A plan that explicitly names a risk, an open question, or a deliberate deferral (even one a reviewer might push back on) passes on honesty regardless of whether the deferral itself is the right call. Otherwise pass. | required |
| Comms respects the thread | The plan comment's own wording, read against the thread highlights' maintainer comments and the repo-facts block's stated contribution/AI policy | Fail if the thread shows explicit maintainer direction — a stated root cause, a request to test a specific patch, a named preferred approach — that the comment does not engage with or acknowledge; or if the repo's stated policy contains an explicit AI-disclosure mandate (it says AI use must be disclosed, naming the tool and extent) and the comment doesn't disclose. A policy that only asks for responsibility/understanding of changes, or no stated policy at all, does not require disclosure. Otherwise pass. | required |

## Verdict rule

Accept (ready to post and build from) only if all six `required` checks
grade `pass`. Any required check graded `fail` or `unclear` makes the
verdict `reject` (hold) — a plan you cannot verify from the package, built
on a cause the evidence doesn't support, or scoped/tested too vaguely to
start from, is not ready to post. There are no `preferred` checks this
week: every failure family the lecture named gates the verdict, because a
plan that is weak on any single one of them is not ready regardless of how
strong the rest is.
