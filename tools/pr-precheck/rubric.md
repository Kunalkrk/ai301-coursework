# Rubric: is this pull request ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Plan fidelity | Every changed file and hunk in the diff, enumerated one by one, read against the plan's stated Files list, its in-scope/not-in-scope lines, and any `## Deviations` note; the description's own fidelity claims ("exactly as planned," "no changes beyond it") read against that same enumeration | Fail if any changed file or hunk falls outside what the plan named in scope and isn't covered by an honest deviation note recorded in the plan (more-than-plan drift — this includes a new flag, option, or feature the plan's not-in-scope line named, even when it reads as thematically adjacent to the fix); or if the diff delivers less than the plan promised with no deviation note explaining the gap (less-than-plan drift); or if the description claims a fidelity the enumerated diff contradicts. A deviation stated in both the plan and the description is honest scoping, not drift, and passes regardless of whether the deviation itself was the right call. Do not grade this from the description's claim alone — list every file the diff actually touches first. Otherwise pass. | required |
| Test evidence | The test-evidence section's before/after output and the diff's own test assertions, read against every *primary* scenario the plan's test plan named (each distinct failure mode or repaired behavior the fix addresses), plus whether the repo's own required checks (test suite, lint, typecheck) were run and their outcome shown | Fail if any primary scenario — a scenario demonstrating the fix itself, or one of several distinct failure modes the plan named as something the fix must address — has nothing concrete shown for it anywhere in the package: neither a before/after transcript nor a specific assertion in the diff's own test code pinning the expected post-condition. A scenario backed by a concrete test assertion in the diff (e.g. `assert x == expected_value`) plus a passing test-suite run counts as shown, but only when that assertion exercises the same observable behavior the plan's test plan named — calling the real affected command/function and checking the real described symptom — not when it calls an internal helper the fix extracted and checks that helper's return value one step removed from the actual repro (a unit test on a flag-derivation function is not evidence the real paged output shows colors; it's evidence the helper returns the right list). A plan's named *control* (confirming unrelated or pre-existing behavior stays unchanged, not demonstrating the fix) is different: a plain stated claim that the control is unchanged passes, as long as nothing else in the package contradicts it and the overall test suite passes — a control doesn't need its own transcript or assertion the way a primary scenario does. Fail also if the shown evidence for a primary scenario exercises a path the fix didn't change rather than the actual repaired behavior; or a claim like "tests pass" or "verified working" appears with nothing concrete backing any primary scenario; or a repo-required check is never run or its output never shown. A required check reported as failing, honestly, with the reason given, is still evidence and does not by itself fail this check — that is a Standards and comms question if the repo requires a clean run, not a Test-evidence one. Otherwise pass. | required |
| Diff quality | Every hunk in the unified diff, and the commit message list | Fail if the diff carries debris: commented-out code (even a single line), dead or unused code (an unreferenced function, a stale TODO), debug print statements, or a hunk that only reformats/re-indents existing code with no behavior change; vague commit messages ("wip," "fix," "cleanup") are a secondary signal, not sufficient alone to fail this. A clean diff containing only the hunks that implement the fix, plus its directly-related tests and docs, passes even when terse. Otherwise pass. | required |
| Standards and comms | The PR title and description read against the repo-facts block's stated PR-template sections and required files (a checklist, a changelog/whatsnew entry), its contribution/AI-disclosure policy, and any explicit maintainer direction in the thread highlights | Fail if a template-required section is left as boilerplate or omitted outright, or a file the template requires (a changelog entry, a whatsnew entry) is simply absent from the diff; or the repo's stated policy contains an explicit AI-disclosure mandate and the description doesn't disclose; or the thread shows explicit maintainer direction the description never engages. A policy that only asks for responsibility/understanding of changes, or no stated policy at all, does not require disclosure to pass; a repo with no PR template has nothing to visibly ignore on that front. Otherwise pass. | required |

## Verdict rule

Accept (ready to submit) only if all four `required` checks grade
`pass`. Any required check graded `fail` or `unclear` makes the verdict
`reject` (hold) — a PR whose fidelity, evidence, cleanliness, or
compliance you cannot confirm from the package is not ready to submit.
There are no `preferred` checks this week: every failure family the
lecture named (silent drift, not tested, unreviewable, standards wall)
gates the verdict, because a PR that is weak on any single one of them
is not ready regardless of how strong the rest is. A PR that honestly
discloses a shortfall — a named, reasoned deviation restated in the
description, not a silently narrower diff — can still be `accept`; the
rubric holds "less than everything" and "not ready" as different
questions.
